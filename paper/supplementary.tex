\section*{Overview}

\section{Summary of previous rounds of reviewing}

In previous rounds of reviewing, the following main topics were discussed:

\begin{itemize}
    \item Rule Expressivity and Tractability: the expressivity of the rules considered in our work covers most of the expressivity capabilities we are aware of when considering state-of-the-art rule mining for LP: AnyBURL covers closed path rules, partially grounded rules and rules with dangling atoms, while AMIE covers pattern based-rules of varying length. The only exception comes from the fact that we omitted AMIE's pattern-based rules with constants due to computational constraints, nonetheless this is a standard tractability trade-off acknowledged in recent literature (e.g., frameworks like pyclause[1] similarly limit this expressivity for scalability and comparability). The partial-grounding component is in any case evaluated from AnyBURL rules. 

    \item Out-Rule Violations and Completeness: our experiments empirically suggest that the contribution of out-rule exceptions at materialization time is limited. In fact from the \#Inc values in Tables 3,4,6,7 it is possible to notice how, after blocking in-rule and in-graph exceptions, the remaining inconsistencies are often 0 or in rare cases (NELL) only limited to a small percentage (less than 1\%) with respect to the generated triples. 

    \item Treating out-rule violations: when handling out-rule violation, the memory requirements would immediately rise as one needs to track provenance of predictions. Additionally, out-rule violations further involve including considerations about confidence and confidence aggregation: a possible heuristic could consider resolving inconsistencies by including a preference based on higher-confidence rules and blocking lower confidence predictions, but this could only be applied with max-aggregation. It is definitely an open question that warrants further analysis, but we kept it outside of the scope to the paper, as their remaining influence is limited.

    \item Schema Availability: the main bottleneck of evaluating more schema restrictions depends on the limited availability of openly available, large-scale KGs that include curated schemas. While industrial applications increasingly focus on the ontological layer, academic benchmarks remain limited. We tried to overcome this by including a synthetic dataset (OWL2Bench) generated from a more expressive ontology, but we were unable to obtain inconsistencies linked to, i.e. inverse functionality. We posit that the three restrictions that we manage to tackle are nonetheless the most widespread and thus beneficial.

    \item Consistency vs. Ranking Performance Trade-Off: we acknowledge that introducing exceptions can slightly decrease standard LP metrics (cf. also the discussion section). However, we argue that this trade-off is in practice unavoidable, as from a downstream application point of view, materializing the standard rule-set will clearly introduce inconsistencies in the KG, which will require a repairing step that with our method can be avoided or heavily limited. This is further supported by the fact that other related work argued for the need of semantic-aware metrics complementary to standard, rank-based ones.
    
    
    
\end{itemize}

\subsection{Repository structure}
\begin{itemize}
    \item \texttt{src/main/java/\allowbreak nmRuleExtension/}: implementation (grounding engines, rule parsers, materialization, evaluation)
    \item \texttt{scripts/}: experiment driver (\texttt{run\_experiments.sh}) and result collection (\texttt{collect\_results.sh})
    \item \texttt{data/[dataset]/}: per-dataset configuration JSON, splits, schema, mined rules and prediction outputs (downloaded from the Zenodo snapshot above)
    \item \texttt{runs/\allowbreak [timestamp]/}: generated logs, \texttt{lp\_results.csv}, \texttt{mat\_results.csv} and \texttt{RESULTS.md}
    \item \texttt{tools/}: rule miners (AMIE, AnyBURL), their per-dataset configurations, and preprocessing notebooks
\end{itemize}

\section{Datasets}\label{sec:datasets}

The five KGs used in the experiments are listed below. Each one is driven by a flat configuration
JSON at \texttt{data/[dataset]/[dataset].json}, pointing at the splits, the schema file, the entity
types file and the four mined rule sets. The prepared versions of all five are contained in the
Zenodo snapshot; the pointers below identify the original sources and the preprocessing applied to
them. Manual preparation steps carried out \emph{after} download (i.e. steps that are not
reproducible by re-downloading) are logged in \texttt{data/DATA\_PREPARATION.md}.

\subsection*{Nell995}
\begin{itemize}
    \item Schema and ontology reachable \href{https://github.com/bagindokemas/SAIKGC?tab=readme-ov-file}{here}
\end{itemize}

\subsection*{CSKG2.0}
\begin{itemize}
    \item Dataset and benchmark reachable \href{https://doi.org/10.5281/zenodo.14167682}{here}
    \item Schema reachable \href{https://scholkg.kmi.open.ac.uk/cskg/ontology}{here}
\end{itemize}

\subsection*{Hetionet}
\begin{itemize}
    \item Splits are generated from the \texttt{pykeen.datasets.hetionet} dataset
    \item Metaedges from hetionet \href{https://github.com/hetio/hetionet/blob/main/describe/edges/metaedges.tsv}{release}
\end{itemize}

\subsection*{YAGO4.5-10}
\begin{itemize}
    \item Data from the official \href{https://yago-knowledge.org/downloads/yago-4-5}{release}
    \item Preprocessing:
    \begin{itemize}
        \item \texttt{yago-disjoints.ttl} manually extracted from \texttt{yago-schema.ttl}
        \item \texttt{properties\_d\_r\_f.csv} manually extracted from \texttt{yago-schema.ttl}
        \item Convert \texttt{yago-facts.hdt} into \texttt{.nt} (rdf2hdt library)
        \item Remove all literals and triples not relevant for LP via \texttt{tools/filterOut\_literals}, obtaining \texttt{yago4.5\_triples.txt} (or \texttt{.nt})
        \item Run \texttt{filter\_ntfile.ipynb} to obtain \texttt{yago4.5-10}
    \end{itemize}
\end{itemize}

\subsection*{OWL2Bench}
\begin{itemize}
    \item Synthetic dataset generated with the OWL2Bench benchmark (Singh et al., ISWC 2020), reachable \href{https://github.com/kracr/owl2bench}{here}
    \item TBox: the OWL 2 RL profile ontology \texttt{UNIV-BENCH-OWL2RL.owl}; ABox generated with the bundled generator (\texttt{tools/setup/\allowbreak OWL2Bench/\allowbreak OWL2Bench.jar}) at a scale of 10 universities, giving $\sim$750k triples
    \item Preprocessing:
    \begin{itemize}
        \item \texttt{tools/setup/OWL2Bench/graph\_to\_dataset.ipynb} converts the generated ABox into the train/valid/test TSVs and the entity types file
        \item Assertions of \texttt{hasResearchInterest} were dropped from the ABox: it is an \texttt{owl:DatatypeProperty} whose single literal object had been rewritten into a pseudo-entity by the TSV conversion, making $\sim$3\% of test triples single-candidate and producing malformed IRIs at materialization time. Its TBox declarations are kept, so the published benchmark ontology is unmodified
        \item The 9 \texttt{owl:AllDisjointClasses} axioms were expanded into their 265 pairwise \texttt{owl:disjointWith} statements (\texttt{UNIV-BENCH-\allowbreak OWL2RL-\allowbreak disjoint-expanded.owl}, used as \texttt{schema} in the configuration), since neither Jena's OWL micro rule reasoner nor an RDFS ruleset reads the RDF collection form
    \end{itemize}
\end{itemize}


\section{Rule miners and configurations}
\begin{itemize}
    \item \textbf{AnyBURL}: 23-1 (\texttt{tools/AnyBURL\_og.jar}). Per-dataset property files are in
    \texttt{tools/setup/[dataset]/}, with \texttt{[dataset]} one of \texttt{NELL}, \texttt{YAGO4.5},
    \texttt{CSKG}, \texttt{hetionet}, \texttt{OWL2Bench}. Two rule sets are mined per dataset with a
    100s snapshot, confidence threshold 0.1 and at least 2 correct predictions:
    \texttt{config-learn.properties} for the full set (cyclic, acyclic and grounded rules, all of
    maximum length 3) and \texttt{config-\allowbreak learn-\allowbreak onlyCP.properties} for the closed-path-only set
    (\texttt{MAX\_\allowbreak LENGTH\_\allowbreak ACYCLIC} and \texttt{MAX\_\allowbreak LENGTH\_\allowbreak GROUNDED\_\allowbreak CYCLIC} set to 0).
    \item \textbf{AMIE3}: 3.5.1 (\texttt{tools/amie3.5.1.jar}), command lines used can be found in
    \texttt{tools/amie\_calls.txt} and \texttt{tools/amiemine.sh}. Rules are mined twice per dataset,
    with \texttt{-maxad 3} and \texttt{-maxad 4}, in both cases with
    \texttt{-mins 10 -minpca 0.1 -minc 0.1 -full}. As discussed above, the \texttt{-const} variant
    (pattern rules with constants) is not used in the experiments.
\end{itemize}

\section{Reproducing the experiments}
\begin{enumerate}
    \item Install dependencies and build (Section~\ref{sec:env}): \texttt{mvn clean install}.
    \item Download the datasets (Section~\ref{sec:datasets}) and extract them into \texttt{data/}.
    \item Run the pipeline. The driver script builds the project, runs the requested stages over the
    requested datasets, tees each stage's output to \texttt{runs/\allowbreak [timestamp]/} and collects the
    metric tables into \texttt{lp\_results.csv}, \texttt{mat\_results.csv} and \texttt{RESULTS.md}.
\end{enumerate}

{\small
\begin{verbatim}
# all stages (lp = link prediction, mat = materialization,
# mateval = violation counting) over the 4 default datasets
# (nell, yago, cskg, owl2bench; hetionet is opt-in)
./scripts/run_experiments.sh

# a subset; dataset keys: nell, yago, cskg, owl2bench, hetionet
./scripts/run_experiments.sh --datasets hetionet --stages lp

# JVM heap for the stages (default 12g; YAGO4.5-10 needs the most)
./scripts/run_experiments.sh --heap 16g

# materialization rule-confidence thresholds (defaults to 1,5,10)
./scripts/run_experiments.sh --stages mat,mateval \
    --percentages 1,5,10

# print the plan without running anything
./scripts/run_experiments.sh --dry-run
\end{verbatim}
}

The individual entry points can also be called directly; each takes a dataset configuration JSON as
its first argument.

{\small
\begin{verbatim}
# Link prediction: both engines, every configured rule set
mvn exec:java -Dexec.mainClass="nmRuleExtension.RunExperiment" \
  -Dexec.args="data/NELL995/NELL995.json [full|anyburl|amie]"

# Materialization: arg 2 = rule-confidence percentages
mvn exec:java -Dexec.mainClass="nmRuleExtension.RunMaterialization" \
  -Dexec.args="data/NELL995/NELL995.json 1,5,10"

# Violation counting over a materialization output directory
MAIN=nmRuleExtension.evaluation.MaterializationEvaluationPipeline
mvn exec:java -Dexec.mainClass="$MAIN" \
  -Dexec.args="data/NELL995/NELL995.json <output dir>"
\end{verbatim}
}

The SPARQL queries used to count the constraint violations reported in the paper are listed in the
repository \texttt{README.md}.
