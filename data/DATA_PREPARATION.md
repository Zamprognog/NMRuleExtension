# Dataset preparation log

Manual preparation steps applied to the datasets **after** they were downloaded from
Zenodo / generated by the notebooks in `tools/`. Anything recorded here is *not*
reproducible by re-downloading — re-apply these steps if you refresh a dataset.

Pre-cleanup copies of every modified file are kept under
`data/<dataset>/data/original/` and `data/<dataset>/rules/original/`.

## OWL2Bench — removal of `hasResearchInterest` (2026-08-19)

### Symptom

Materialization output contained malformed N-Triples with doubled angle brackets:

```
<http://benchmark/OWL2Bench#U1C0D2SS0> <http://benchmark/OWL2Bench#hasResearchInterest> <<hasResearchInterest_SomeResearchTopic>> .
```

5,245 of 62,678 lines in
`OWL2Bench_anyburl_FULL_semantic_10_rules_20260817_232639.nt` were affected, and the
same pattern appeared in all four `.nt` files of that materialization run.

### Root cause

A chain of three issues, none of them in the grounding logic:

1. In the original OWL2Bench graph, `hasResearchInterest` is an **`owl:DatatypeProperty`**
   (`UNIV-BENCH-OWL2RL.owl`, `rdfs:range rdfs:Literal`) whose object is the literal
   `"SomeResearchTopic"^^xsd:string`.
2. The TSV conversion replaced that literal with a synthetic pseudo-entity named
   `<hasResearchInterest_SomeResearchTopic>` — **with the angle brackets baked into the
   string itself**. It was the only bracketed term in any dataset TSV.
   `DataLoader` does not strip brackets, so the token flowed through grounding verbatim.
3. `Materializer.writeToNTriples()` wraps every term in `<...>` unconditionally, producing
   `<` + `<hasResearchInterest_SomeResearchTopic>` + `>`.

Even without the doubling the term was unusable: `<hasResearchInterest_SomeResearchTopic>`
is a *relative* IRI, which GraphDB rejects.

### Why the property was dropped rather than repaired

The property is **degenerate**: it has exactly **one distinct object** across the entire
dataset. Every one of its 11,373 train / 294 valid / 302 test triples points at the same
constant. Consequences for the experiments:

- ~3% of test triples were free wins — a single candidate means guaranteed MRR = 1 / Hits@1
  for *both* grounding engines, inflating the absolute numbers with no signal.
- 1,247 of 25,133 AnyBURL rules (~5%) and 94 of 541 AMIE-4CP rules referenced it, many at
  confidence 1.0 (`hasResearchInterest(X, <…SomeResearchTopic>) <= …`) purely because there
  was nothing else to predict.
- Minting a proper IRI instead would have left an `owl:DatatypeProperty` with an IRI object —
  a standing `rdfs:range` violation, i.e. exactly the error `SemanticGroundingEngine` exists
  to detect. The semantic engine would have been scored against a schema its own data
  contradicted.

This also aligns the dataset with the project's general policy: `tools/filterOut_literals.sh`
strips all literal-valued triples. This one only survived because it had already been
rewritten into a pseudo-entity before that filter ran.

### What was changed

All triples with predicate `http://benchmark/OWL2Bench#hasResearchInterest` were removed
from the ABox. **TBox declarations were kept** — the property still exists in
`UNIV-BENCH-OWL2RL.owl` and in the two schema triples inside `OWL2Bench_full_graph.nt`
(`rdf:type owl:DatatypeProperty`, `rdfs:range rdfs:Literal`). Only the assertions are gone,
so the published benchmark ontology is unmodified.

| File | Before | After | Removed |
|---|---:|---:|---:|
| `data/OWL2Bench_train.tsv` | 386,511 | 375,138 | 11,373 |
| `data/OWL2Bench_valid.tsv` | 10,171 | 9,877 | 294 |
| `data/OWL2Bench_test.tsv` | 10,172 | 9,870 | 302 |
| `data/OWL2Bench_full_graph.nt` | 762,316 | 750,347 | 11,969 |
| `rules/OWL2Bench_rules_anyburl_ALL-100` | 25,133 | 23,886 | 1,247 |
| `rules/OWL2Bench_rules_anyburl_CP-100` | 504 | 390 | 114 |
| `rules/OWL2Bench_rules_amie_4CP.tsv` | 541 | 447 | 94 |
| `rules/OWL2Bench_rules_amie_3CP.tsv` | 56 | 50 | 6 |
| `rules/OWL2Bench_4CP_rules.tsv` | 587 | 493 | 94 |
| `rules/OWL2Bench_3CP_rules.tsv` | 62 | 56 | 6 |

`data/OWL2Bench_rules_anyburl_ALL-100` (a stray duplicate of the file in `rules/`) was
filtered identically. `OWL2Bench_entity_types.nt` contained no occurrences.

Commands used (predicate matched on column 2 only, so entity names are never touched):

```sh
P='http://benchmark/OWL2Bench#hasResearchInterest'
awk -F'\t' -v p="$P" '$2 != p' <tsv>                      # train / valid / test
awk -v p="<$P>" '$2 != p' OWL2Bench_full_graph.nt          # ABox only, TBox survives
grep -v 'hasResearchInterest' <rule file>                  # all rule files
```

### Post-conditions verified

- Zero bracketed terms remain in any OWL2Bench TSV.
- Relation vocabulary: 39 → 38.
- Entity vocabulary: 50,238 → 50,237 — the only entity lost is the pseudo-entity itself.
- Entities in valid/test unseen in train: unchanged (17 valid, 21 test). No new orphans.
- The two `hasResearchInterest` TBox triples are still present in the graph.

### Rule re-mining (2026-08-19, after the cleanup)

Both miners were re-run on the cleaned train split. Two traps were hit and are worth
recording, because both silently produce *stale* rules that still look plausible:

**1. AnyBURL reads its own copy of the data.** `tools/setup/OWL2Bench/config-learn.properties`
and `config-learn-onlyCP.properties` set `PATH_TRAINING = ./setup/OWL2Bench/OWL2Bench_train.tsv`
— a copy inside `tools/setup/`, *not* `data/OWL2Bench/data/`. (The path to the real dataset is
present in both files but commented out.) The first re-mine ran against the stale May 22 copy
and produced rules still containing 1,835 `hasResearchInterest` references and 1,565
occurrences of the `<hasResearchInterest_SomeResearchTopic>` pseudo-entity — a token with zero
occurrences in the cleaned train split. **Sync `tools/setup/OWL2Bench/OWL2Bench_{train,valid,test}.tsv`
from `data/OWL2Bench/data/` before mining**, or flip the config to the commented-out path.
(The `tools/setup/` copies were synced afterwards and are clean as of 2026-08-19 — verified zero
`hasResearchInterest` occurrences in both the copies and the rule files they produced.)

Invocation (run from `tools/`, ~100 s each; `SNAPSHOTS_AT = 100` names the `-100` output):

```sh
cd tools
java -Xmx8g -cp AnyBURL_og.jar de.unima.ki.anyburl.Learn setup/OWL2Bench/config-learn.properties
java -Xmx8g -cp AnyBURL_og.jar de.unima.ki.anyburl.Learn setup/OWL2Bench/config-learn-onlyCP.properties
cp setup/OWL2Bench/OWL2Bench_rules_anyburl_{ALL,CP}-100 ../data/OWL2Bench/rules/
```

**2. AMIE output needs the alignment step.** `tools/amiemine.sh` writes *raw* AMIE output
(banner + header + footer lines) to `OWL2Bench_{3,4}CP_rules.tsv`. The experiment config reads
`OWL2Bench_rules_amie_{3,4}CP.tsv`, which are the **aligned** files produced by
`tools/align_amie_rules.ipynb` — it converts AMIE's format to AnyBURL's
(`body size \t positive examples \t std confidence \t rule`), keeps only
`Body size > 1 AND Std Confidence < 1.0`, and sorts by confidence. Running `amiemine.sh` alone
leaves the config pointing at whatever the aligned files held before. Remember to run the
notebook (set `dataset`/`rtype` at the bottom) for **both** 3CP and 4CP.

Rule counts after a correct re-mine on the cleaned data:

| Rule set | Pre-cleanup | Stopgap (filtered) | Re-mined |
|---|---:|---:|---:|
| `anyburl_ALL-100` | 25,133 | 23,886 | 21,333 |
| `anyburl_CP-100` | 504 | 390 | 388 |
| `amie_4CP` (aligned) | 541 | 447 | 447 |
| `amie_3CP` (aligned) | 56 | 50 | 50 |

The AMIE 3CP set is identical to the filtered stopgap; 4CP has the same size but 36 rules
differ, since AMIE's search over the cleaned graph settles on a slightly different set.
AnyBURL ALL-100 shrinks well below the filtered stopgap (23,886 → 21,333): beyond the 1,247
rules that named the property directly, others had been mined *through* it.

Verified post-conditions: zero `hasResearchInterest` occurrences in any rule file or split.

### Follow-up (done)

Rule re-mining is done (see above). Any OWL2Bench numbers produced before 2026-08-19 are
not comparable to numbers produced after — the test split lost 302 triples and the rule sets
changed. Experiments and materializations were re-run with
`./scripts/run_experiments.sh --datasets owl2bench`; the authoritative results are
**`runs/20260819_142132/`** (also the source of the OWL2Bench rows in the paper).

Superseded: the OWL2Bench rows in `runs/20260817_210448/` are pre-cleanup and must not be reused
(e.g. AnyBURL_ALL Standard MRR 0.2458 there vs 0.2223 after the cleanup).

### Known remaining issue (not fixed here)

`Materializer.writeToNTriples()` (`src/main/java/nmRuleExtension/materialization/Materializer.java:205`)
still wraps terms in `<...>` with no validation. With OWL2Bench cleaned there is no dataset
that triggers it, but a future dataset carrying a non-IRI or pre-bracketed term would
silently emit invalid N-Triples again.

## OWL2Bench — disjointness axioms expanded (2026-08-19)

### Why

OWL2Bench states most of its class disjointness with **`owl:AllDisjointClasses`**, an OWL 2
construct that wraps its members in an RDF collection:

```
_:Ncdeb11d8... rdf:type    owl:AllDisjointClasses .
_:Ncdeb11d8... owl:members _:N0c6021a9... .          # rdf:first/rdf:rest chain
```

There are 9 such axioms (group sizes 10,10,10,10,10,7,5,4,3), encoding **265 pairwise
disjointness constraints**, plus only 3 plain `owl:disjointWith` triples.

Nothing in the stack reads the collection form:

- **`SemanticConstraintLoader`** extracts disjointness with Jena's `cls.listDisjointWith()`
  (`SemanticConstraintLoader.java:173`), which sees only direct `owl:disjointWith` triples.
  The model uses `OntModelSpec.OWL_MEM_MICRO_RULE_INF` (line 55) — an OWL 1-era rule reasoner
  with no `owl:AllDisjointClasses` support. Runs logged
  `SemanticGraphManager: Extracted 6 disjoint class mappings` — the 3 triples in both
  directions, against 265 constraints it never saw. This likely explains why every OWL2Bench
  materialization reported **0** domain- and range-disjointness violations while functional
  violations ran to tens of thousands.
- **GraphDB under `rdfs-optimized`** parses the blank nodes fine (parsing is ruleset
  independent) but RDFS has no disjointness semantics at all, so both the collection form
  *and* plain `owl:disjointWith` are inert — no inference, no consistency checking.

Note the `.owl` file is **not** a more tractable source: it writes these axioms with
`rdf:parseType="Collection"` (31 uses), which is RDF/XML sugar expanding to the identical
blank-node + `rdf:first`/`rdf:rest` structure. Easier for a human, identical to a parser.

### What was generated

Two new files. **Neither the benchmark ontology nor the full graph was modified.**

| File | Contents |
|---|---|
| `data/OWL2Bench_disjointness_expanded.nt` | 530 N-Triples — the 265 pairs, both directions |
| `data/UNIV-BENCH-OWL2RL-disjoint-expanded.owl` | copy of the ontology with those 530 statements appended as RDF/XML |

Generated by walking the `owl:members` collections in `OWL2Bench_full_graph.nt` and taking
the pairwise closure of each group. Both directions are emitted explicitly: `owl:disjointWith`
is symmetric, but neither RDFS nor a plain triple store infers that.

Validated: 530 lines, all well-formed `<iri> <iri> <iri> .`; 68 distinct classes; symmetry
complete (0 missing reverses); no self-disjointness; 0 pairs duplicated an existing axiom;
the merged `.owl` is well-formed XML.

Measured effect on the Jena extraction (loading each TBox through `SemanticConstraintLoader`):

| TBox | classes with disjointness | directed pairs |
|---|---:|---:|
| `UNIV-BENCH-OWL2RL.owl` | 6 | 6 |
| `UNIV-BENCH-OWL2RL-disjoint-expanded.owl` | 74 | 536 |

### How to use them

- **GraphDB:** load `OWL2Bench_disjointness_expanded.nt` alongside `OWL2Bench_full_graph.nt`.
  Disjointness then answers a plain `?a owl:disjointWith ?b` pattern under any ruleset.
  RDFS still will not *detect* violations for you — that needs a SPARQL query, or a ruleset
  with disjointness semantics (`owl2-rl`).
- **This pipeline:** point `"schema"` in `data/OWL2Bench/OWL2Bench.json` at
  `UNIV-BENCH-OWL2RL-disjoint-expanded.owl`. No Java change needed.
  **Done on 2026-08-19** — the config now uses the expanded TBox, and the run logs confirm the
  effect: `SemanticGraphManager: Extracted 74 disjoint class mappings` (was 6).

### What the expanded disjointness actually changed

Less than expected. The all-zero disjointness columns were **not** caused by the missing axioms:

- In materialization evaluation (`runs/20260819_142132/owl2bench_mateval.log`, run with the
  expanded TBox) domain- and range-disjointness violations are still **0** across every
  materialized file, while functional-property violations remain large (e.g. 37,571 of 113,178
  triples for AnyBURL FULL standard @10%). So the hypothesis recorded above — that the missing
  `owl:AllDisjointClasses` expansion explained the zeros — is **disproven**. The materialized
  triples simply do not assert types that conflict with any declared domain/range.
- Link-prediction Sem@k for the semantic engine was already 1.0 before the change and still is,
  so the extra constraints did not prune any additional ranked candidate either.

The expanded TBox is still the right input to keep — it makes the constraint set faithful to the
benchmark — but it is not the reason the disjointness numbers are zero.

## YAGO4.5-10-flip — inverse-functionality variant (2026-08-25)

Derived dataset built for the inverse-functionality analysis (paper Section 5.1.1). Unlike the
other entries in this log it *is* reproducible from a script, but it is recorded here because the
generated files are ~1.2 GB and are therefore **not** archived on Zenodo: a reader rebuilds them.

### Why

YAGO4.5-10 declares four functional properties and no inverse-functional ones, so the
inverse-functionality branch of `SemanticGroundingEngine` had no dataset to exercise. Of the four,
only two are usable: `schema:gender` has nine distinct objects and once inverted would return the
whole `Person` population for every query, and `schema:publisher` occurs in 16 triples with
blank-node domain and range. The remaining two, `schema:birthPlace` (140,221 triples) and
`schema:deathPlace` (55,941), are flipped.

### What is generated

`yago_flip_experiment/flip_yago.py` rewrites every `(s,P,o)` as `(o,P^-1,s)` in the train/valid/test
TSVs and in the full `.nt`, so triple counts, entities and split boundaries are unchanged
(3,222,052 / 16,273 / 16,273; full graph 3,997,045 lines including `rdf:type`). The entity types
file is copied verbatim — flipping changes a statement's direction, not the entities in it. In the
T-Box the original property's axioms are dropped and the inverse (`yago:birthPlaceOf`,
`yago:deathPlaceOf`, minted in the YAGO namespace since schema.org does not define these terms) is
declared `owl:InverseFunctionalProperty` with domain and range **swapped**. No `owl:inverseOf` is
emitted, so no twin relation is left for a rule to invert at no cost.

Six files land in `yago_flip_experiment/data/`, all gitignored.

### How to rebuild and check

```sh
cd yago_flip_experiment
python3 flip_yago.py      # needs prepared data/YAGO4.5/data/ as input
python3 verify_flip.py    # exits non-zero on any failure
```

`verify_flip.py` checks that counts are conserved per split, that both flipped properties are
empirically inverse functional, that no occurrence of the originals is left, that the flipped
triples raise no domain or range violation through the `subClassOf` closure, that the flip
introduces no new reciprocal-relation leakage, and that the six files match the sha256 manifest in
`yago_flip_experiment/CHECKSUMS.md`. Regenerate the manifest with `--write-manifest` only after a
deliberate rebuild.

### Rules (not reproducible — archive these)

The mined rule sets are **not** regenerable: AnyBURL is time-budgeted (`SNAPSHOTS_AT`) and
multi-threaded (`WORKER_THREADS = 4`), so re-mining yields a different rule set and different
numbers. `yago_flip_experiment/rules/` is gitignored and ships in the Zenodo snapshot instead.

The paper uses `config-learn-flip-IFP.properties`: AnyBURL in the `Full` setting with
`SINGLE_RELATIONS` restricted to the two inverse-functional heads, `THRESHOLD_CONFIDENCE` 0.01 and
a 300s snapshot, yielding 20,562 rules. Both deviations from the main configuration (which uses
0.1 and 100s) are deliberate and are documented in the paper: rules with these two heads are
individually low-confidence and are almost absent from the top-1/5/10% of an unrestricted run,
which would leave the constraint untested. Absolute figures are therefore not comparable with the
main tables — only standard vs. nmr within the experiment is.

`config-learn-flip.properties` and `config-learn-flip-CP.properties` are the unrestricted runs that
motivated the restriction; they are kept for provenance but the paper does not use them.

### Where the published numbers come from

Tables 8 and 9 are counted from `yago_flip_experiment/logs/mateval_ifp.log` and
`mateval_ifp_std5.log`; the applied/target rule counts and timings come from the breakdown blocks
in `logs/mat_ifp.log`. Those logs are tracked in git.
